# Harness Coding 规范（通用）

> **文档状态**：模型无关、项目无关的**通用 harness 规范**
> **核心**：**有规划（Plan）→ 有测试（Test）→ 有反馈（Feedback）**
> **定位**：给 AI 编码套上工程"挽具"（harness），取代无约束的 Vibe Coding；
> 使不同模型、不同工具、不同开发者产出**一致、可验证、可追溯**的结果。
> **关联**：[agents/Readme.md](./Readme.md)（项目级落地约定）· [docs/rules/Development.md](../docs/rules/Development.md)

---

## 1. 为什么是 Harness，而不是 Vibe

| 维度 | Vibe Coding（无约束） | Harness Coding（本规范） |
| --- | --- | --- |
| 入口 | 一句需求，直接生成 | 先规划：读规范 → 定位影响面 → 列步骤 |
| 验证 | 跑不跑得通看运气 | 有测试：改动必有测试，跑通才算完成 |
| 闭环 | 一次生成即结束 | 有反馈：结果回写文档/版本/测试，形成闭环 |
| 一致性 | 每次结果可能不同 | 规范约束下，模型切换结果一致 |
| 可追溯 | 无记录 | 迭代记录 + 提交规范 + 版本文档可追溯 |

---

## 2. 三要素闭环

### 2.1 有规划（Plan）

1. **先理解，再动手**：读项目规范、页面文档、现有实现，明确改动边界。
2. **定位影响面**：列出会触碰的文件、模块、文档、测试。
3. **分解步骤**：多步任务先列计划（如 todo 列表），逐步执行、逐步验证。
4. **选最小路径**：优先最小改动，不顺带重构无关代码。

### 2.2 有测试（Test）

5. **改动必有验证**：功能/页面/接口变更后，必须有对应测试或可执行验证。
6. **增量优先**：只跑受影响范围的测试；大规模重构/发版前才跑全量。
7. **验收可复现**：构建 + lint + 测试通过，才算完成；失败要定位到根因而非绕过。

### 2.3 有反馈（Feedback）

8. **结果可追溯**：把变更写入项目记录（迭代记录 / 变更日志 / 版本文档），而不是只在对话里说。
9. **文档随代码走**：功能/界面/接口/依赖变更，同步对应文档。
10. **提交有语义**：提交信息简短、语义化（Conventional Commits），便于回溯。
11. **失败要回报**：报错、失败、不确定处如实汇报，不隐藏、不猜测蒙混。

## 3. 通用行为准则（模型无关）

1. **不臆造**：不编造 API、参数、文件路径；不确定时先查证（读代码/文档/实测）。
2. **不越界**：不改与当前任务无关的文件；需要重构先说明并获确认。
3. **最小惊讶**：保持既有风格（命名、目录、语言、框架约定），不引入项目未使用的新依赖/新范式。
4. **双语一致**（如项目要求 i18n）：面向用户的文案必须同步所有语言版本。
5. **权限边界**：提交、推送、发布、删除等不可逆操作，须用户明确指令后执行。
6. **如实汇报**：完成什么、改了哪些文件、验证结果、遗留问题，清晰列出。

## 4. 工作流模板（可复用）

```
1. 读规范     → 项目规范 + 页面文档 + 现有实现
2. 定影响面   → 文件 / 模块 / 文档 / 测试清单
3. 列计划     → 分解为可执行步骤（todo）
4. 实施       → 最小改动；保持既有风格
5. 验证       → 构建 + lint + 增量测试通过
6. 同步文档   → 页面/版本/架构/依赖/技能对应文档
7. 汇报       → 改了什么、验证了什么、遗留什么（不自动提交/推送）
```
